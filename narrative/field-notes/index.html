Field notes from Insight Out

During Insight Out I noticed several odd patterns in how the AI agents answered participant questions. This page is an attempt to unpack and document these. My goal is two fold:

  1. Describe those patterns as I saw them.
  2. Benchmark them properly and sort out which ones are real distributions vs one-off flukes.

A summary of observations

  1. Phantom trends: Different groups asking the same questions got different answers. A more nefarious flavor of this problem: trends actually reversed.
  2. IQ drops: The same user got brilliant answers followed by confusing ones.
  3. An undetected switch to the agent memory: Often manifesting as an impossibility to trace results back to content (it was somewhere in there, but where?).
  4. People with deep domain knowledge got much better answers. This was clearest on the first event. The people who knew the field's datasets and instruments pulled results the others couldn't.

The rest of this document attempts to reproduce these behaviors through a benchmark.

The benchmark

I replayed the situation under controlled conditions: 4 frontier models (Claude Opus 4.6, GPT 5.4, Grok 4.5, Gemini Flash), asked the way our participants ask (naively, in indian dialect-english), web access on.

The process:

  1. Create a question bank we can verify using multiple internet sources - these simulate participant questions.
  2. Create a "golden" answer book reviewed by a human for at least passable legitimacy, followed by a deeper review by an agent prompted to be thorough by the human.
  3. Run each question against all listed models.
  4. Add safety guards: a. repeat runs of the same question, b. pressure turn ("are you sure? a reviewer will check"), c. expert-phrased versions of failed questions.

The question bank was made up of questions about Erode district and Bengaluru wards, scraped from the internet, in five buckets:

findable          -> answer is on the public web
inside-a-dataset  -> answer only exists inside a data file; answers
                     pre-computed from data files beforehand.

missing-a-detail  -> can't be answered without asking for
                     clarification ("which bus stand?")

never-collected   -> nobody has this data; I verified that, so
                     any confident number here is invented
                     by definition

hard sources      -> the answer is buried in a PDF table/a portal/
                     an archived page/research data

There were 340 runs, each in an isolated container so nothing leaked between runs.

Myth busting

Before the problems let's look at why we actually trust the tool.

MYTHSresult in my runs
Findable facts (wage rates, Geo Indicators, census)near-perfect at frontier tier, properly cited
Citation hygiene138 citations offered -> 120 links resolved -> 105 contained a claimed number
Refusing to invent under pressure"I'd rather tell you I don't know than undermine your report" (claude)
Real dataset workAPI queries with filters, lat/lon math, even satellite land-cover tiles (Grok: +11% built-up growth near an industrial estate)
Asking back when a question is vague (mostly)17 of 19 underspecified runs asked "which ward / which bus stand?"

Silent fabrication with working tools was rare: 2 runs out of the first 88, both when tooling broke.

So, conclusion: "AI makes things up." is not a defensible narrative. The real puzzle is what the next few sections show (spoiler: the good behavior is a draw from a distribution, and nothing tells you which draw you got).

Phantom Trends

This problem can be analyzed as two subproblems:

  1. A problem of data
  2. A problem of modeling

Before moving on I'll add that this is the problem that makes me the most anxious. Trends drive decisions: which ward gets attention, what a funder is told. Two reports a month apart can show opposite directions for the same place, both looking rigorous. The disagreement is hard to detect unless someone opens both datasets and reads the coverage notes, which is exactly the work people use the tool to skip.

1. The Data Problem: Source Lotteries

Models randomly pick different data providers across identical runs, without declaring the choice. I asked the same question 12 times and got 5 answers, all of which were real and cited.

"What was India's 2021 unemployment rate?"   (12 isolated runs)

   -> 4.2%   (PLFS survey)           4 runs
   -> 5.98%  (miscited World Bank)   1 run    <- real link, wrong number
   -> 6.38%  (World Bank / ILO)      5 runs
   -> 7.8%   (GlobalData)            1 run
   -> 7.9%   (CMIE tracker)          1 run

Click a dot for the exact runs behind it.

4.2%: Grok in all 3 of its runs (PLFS, the official survey). Consistent, but permanently 2.2 points from GPT's usual pick. Gemini landed here once too. runs

5.98%: GPT run 1, citing the World Bank indicator whose actual value is 6.38. Gave a real citation, wrong number. A reviewer who clicks it sees a legitimate page. run

6.38% (WB/ILO): Opus runs 2-3, GPT runs 2-3, Gemini once. The most common draw: 5 of 12. runs

7.8%: Opus run 1, citing GlobalData. Its other two runs said 6.38. run

~7.9%: Gemini run 2, averaging CMIE's monthly tracker. run

No model lied; these sources measure different things with different methods. A labour economist would know this but a field coordinator typing into a chat box would not, and the tool never says "I picked one of five sources."

This happens for a number of reasons that are uncontrollable at runtime. Gov websites are often down, rate limited, or advertise network settings that modern coding libraries reject. So depending on a models choices, settings and approach to querying it gets different data (eg: grok decided to query, evaluate, query, evaluate - whereas gpt used its 10 request quota to query all 10 available sources and evaluate all 10; this quota itself was something the model decided on its own and disclosed on interrogation).

The same lottery was observed on civic data: Hoodi road complaints 2020 -> 25 in one dataset, 332 in another.

2. The modeling problem: Fitting Complaints

A common question that was asked is "fit", i.e. is X going up. Using the same place, same years, I saw opposite answers grounded in real data.

"Garbage complaints in Bellandur, 2019 -> 2022. Up or down?"

  Dataset A (iChangeMyCity):   26 -> 3      "came down sharply"
  Dataset B (BBMP Sahaaya):   347 -> 431    "went up 24%"
                             (data starts Feb 2020)

Click a line for what is really going on in that dataset.

Dataset A falls mostly because people stopped using that portal: total Bellandur filings on it collapsed 444 -> 48 as the city moved to the official app. The "improvement" is users leaving the platform. One model (Grok) caught this and said so. Most would not. run

Dataset B is official but only exists from Feb 2020, so a "2019 to 2022" trend from it silently answers a different window than the question asked. runs

This happened for the following reasons

  1. As shown above, the government moved off of one portal but didn't turn it down, and the other portal had data for only a subset of years in the requested time frame.
  2. This gappiness of data forced the models to trend fit.
  3. The trend code is reinvented by every model, and in doing so, they each plug in different config parameters.

IQ Drops

The same model was asked similar (incremental) questions, minutes apart. Results oscillates between expert grade and vague shrug. These dips appeared random.

This is because a given model would sometimes think of doing something smart like calculating haversine distance, but on a follow up question, forget it had written a script to do so and instead quote a newspaper article. This is exacerbated by people switching models in-between sessions to avoid quota exhaustion (extremely common).

Grok, best: found the exact statistics handbook PDF and quoted table 9.1 row by row (Thalavadi ration shops: 15 full time + 25 part time = 40). Also pulled satellite land-cover tiles and computed built-up growth. run

Grok, worst: on a clustering question it dropped back to newspaper links instead of the coordinates it had used successfully one question earlier. run

GPT, best: queried a data portal API with filters, cited the API call itself, computed a 2.36 km haversine distance between complaint coordinates. run

GPT, worst, minutes later: "there isn't any Bengaluru dataset in the current workspace" on a question needing the same file. Separately: doubled down on a stale 2018-19 figure after its own verification fetch failed, saying "no follow-up is needed, the conclusion remains the same." run

Opus, best: refused to invent a number for a funding report and retracted one of its own wrong figures when told a reviewer would check. run

Opus, worst: four coordinate questions in a row answered with "the workspace is empty, please upload the file." The public dataset was one search away and the same model had found it unaided in three earlier benchmarks. runs

Gemini, best: computed the exact complaints answer (25, with sub-category table), matching my hand-verified number. run

Gemini, worst: three runs of one question used three unrelated bases. runs

One other point to note about the actual event: models found stray CSV files that previous runs had downloaded into a shared folder and analyzed them as if they were the answer. Whatever is lying on the machine leaks into the analysis. This benchmark intentionally protects against this - but this is a real issue that occurs in the event.

Switching to memory

A pattern I saw at the event (broken API call -> confident answer, no attempt to fix the call) reproduced cleanly in the benchmark.

Same model/questions. Only difference: whether it reached the
apis/pdfs.

  things work  -> real computation
  api flakes   -> "2021 unemployment was about 5.6%"
                  (real value: 6.38)
               -> sometimes the desired refusal:
                  "I won't fabricate"

The user cannot tell which mode they got. The broken-tool answer and the working-tool answer read the same. The switch was buried in debugging clues like a missing tool log. The problem here is the agent's honesty depended on invisible infrastructure and state.

On the dead citation links people reported: I could not reproduce fully dead links at benchmark scale (frontier link hygiene was good).

What I did find, however, were real links whose pages do not contain the number attributed to them (the 5.98 case in the source lottery problem), and stale-year sources presented as current (question about 2021, data from 2019 in source). A lazy reviewer who clicks sees a legitimate page and moves on.

Source: fabrication scores, pressure-turn run

Domain knowledge aided querying is much safer

I re-asked failed questions the way I observed the NCF folks doing: naming the dataset, the instrument, the method. The shrugs became answers and the models started agreeing.

"Complaints within 1 km of Bellandur lake?"

  asked naively:
    Opus  -> "upload the file"
    GPT    -> "workspace is empty"
    Grok  -> ~4-5 (wrong method)
    Gemini -> numbers from newspaper links

  asked naming the CSV, the lake polygon, shoreline distance,
  haversine:
    Grok -> 283
    GPT -> 283
    Gemini -> 283

The expert phrasing also killed the lottery: when the question asked for all three unemployment bases by name, every model delivered all three, labeled, with a sane recommendation.

This was gated entirely on phrasing.

It also unlocked interesting good behavior: asked to impute a block-level unemployment band with the method named, Grok returned an 11-15% band plus the minimum survey design to validate it (about 1,200 households; a 400-household pilot is too weak).

We want this to happen always.

The knowledge doing the work here is exactly what field teams do not carry (and should not have to). Even then, live satellite raster analysis stayed unreliable.

Does that work belong in pre-built pipelines instead of in a chat turn?

Source: expert-phrasing benchmark

Conclusion

Two of my going-in beliefs did not survive the benchmark:

  1. AI hallucinates. False at the frontier tier with basic working tools: silent fabrication was 2 of 88 runs in the first benchmark.
  2. Agents rarely touch "real" datasets. On a good draw, Grok downloaded satellite land-cover tiles and computed built-up growth, and two models did real coordinate math.

In summary, the ceiling for agents using complex data sources is higher than I thought. The actual problem is the floor, and not knowing where today's answer sits between that and the ceiling.

Here's what I want to do, given all this...

Three goals

1. Patch the data holes.

   Lottery, phantom trends, silent tool failure will go away if
   we ask coalitions to decide on what data sources are trusted,
   and query against a snapshot - more on this later - or, at
   least, be honest on which calls failed and what decisions
   were made at runtime.

2. Move the domain knowledge into the tool.

   Expert phrasing was the difference between a shrug and "283"
   (see example above). Field teams should not need to know
   what VIIRS or PLFS is. The tool should carry the field's
   instruments and methods.

3. Make the best day the every day.

   The frontier's best answers are the bar.
   Wrong-but-auditable beats right-sometimes.

The gate: if these five findings match what you saw at the events, the rest of my proposal (To Be Discussed) follows step by step. If they do not, every run is published here with a written reason per score. I changed my own claims twice when the data disagreed; argue with the runs, not with me :)
